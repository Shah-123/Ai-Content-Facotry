### Research agent (Tavily + scraping + evidence extraction)
*How latency is composed:* research_node (research.py:182-321) is one graph node with three strictly sequential phases and exactly 1 LLM call; it sits on the critical path to the HITL plan screen (router -> [document_ingest] -> research -> orchestrator, main.py:509-542, interrupt_after orchestrator at :610).
1) Tavily: <=5 queries in a pool of 5 (research.py:207-236). The deprecated langchain_community TavilySearchResults is used with its default search_depth="advanced" and a requests.post that has no timeout (verified in the langchain-community 0.4.2 wheel). The `days` arg is silently dropped. Author comment says ~4s per query (:201-203). Estimate 3-8s.
2) Scrape: up to 15 URLs, pool of only 5 = 3 waves (:254-274). Each URL is Jina (timeout=8, Accept: text/event-stream) and, on failure, a SECOND serial direct fetch (timeout=10) plus html.parser (:127-179). The author observed 4/10 Jina timeouts (:160-162). Worst case per URL is ~18s. The phase waits for all 15 futures (no early exit). Estimate 20-45s.
3) Extraction: ONE serial structured-output call on llm_fast (gpt-5-mini, default reasoning effort; grep finds no reasoning_effort anywhere in Agents_backend). Input is ~15 x 3000 chars (~11-15k tokens). Output is 8-10 items with 50-200 word snippets. The UI sees nothing until it returns (:285-299). Estimate 25-60s.
Total estimate 50-110s, no sleeps, no caches, no early exit. Scrape plus LLM are ~85-95% of it. Dedup/merge CPU is negligible (<10ms at <=25 results). All numbers are estimates, not measurements.
Measure first: the research.py _emit calls at :183/:205/:256/:283/:318 are written with timestamps to Agents_backend/data/events/<job>.jsonl (event_bus.py:214-219; clear_job is never called outside tests), so phase times can be read from existing runs. For the LLM split, log usage_metadata["output_token_details"]["reasoning"], which usage.py:235-247 currently drops.

Other findings noted but not listed as latency items: the Tavily recency window is a silent no-op (see RES-5); `{e.url: e}` at :301 keeps only the last item per URL; an extractor exception is uncaught, so the job fails after up to 3 x 180s.

### Document ingest and RAG (upload, chunking, embeddings, Chroma, retrieval)
*How latency is composed:* UPLOAD (POST /api/uploads -> asyncio.to_thread(ingest_upload), uploads.py:62-65). Every step is serial and the UI's Generate button stays disabled until it returns (ChatView.tsx:730-734): parse (pypdf, measured 8 ms/page on the local 70-page thesis, so negligible) -> embed every sentence (OpenAIEmbeddings.embed_documents loops serially over 1000-input batches; 2,187 sentences = 3 requests, a 200-page doc is about 6-7) -> Python cosine-distance loop (measured 0.46 s per 5,000 sentences) -> embed all chunks again (second pass, about 1 request) -> Chroma upsert (local PersistentClient, cold-start import/init on first use) -> embeddings.json write (measured 0.31 s for 330x1536 floats) -> derive_topic gpt-5-mini call (default reasoning effort, serial, tail of the request) -> meta.json.
JOB TIME (document_ingest_node, document_ingest.py:679-820, sits serially between router and research, main.py:509-541): new OpenAIEmbeddings client + embed_query (1 request) -> Chroma query (cold init on first call) -> 8 gpt-5-mini structured-output extraction calls through ThreadPoolExecutor(max_workers=4), i.e. 2 sequential waves, each producing 3-6 facts with 50-200 word snippets at default reasoning effort. That extraction is the dominant cost (estimate 15-40 s). The three-tier fallback only costs time on failure.
The node overlaps with nothing, although research_node only needs the document evidence at its final merge (research.py:244, 303-312).
Chroma and retrieval are cheap once warm. The latency is LLM extraction, serial embedding batches, the derive_topic call at the end of upload, and the missing overlap with router and research.
All seconds below are estimates unless marked measured. Measured: pypdf 8 ms/page, json.dump 0.31 s, distance loop 0.46 s vs 0.24 s vectorised. Estimates assume gpt-5-mini at about 100 output tokens/s with 400-1500 reasoning tokens per call.

### Parallel workers, reducer, completion validator, templates
*How latency is composed:* Default API job (schemas.py:4-28): sections=3 -> N = 3+4 = 7 writers (orchestrator.py:8-10,120; max 10+4 = 14). The user always approves the outline first (background.py:223-235), then Phase 2 runs (background.py:269).
Critical path after approval: fanout() emits one Send per task (workers.py:94-113). Workers are sync nodes, so LangGraph runs them on a thread pool. That is real I/O parallelism, and stage time is the slowest worker. Each worker makes 1 LLM call: ~3.2-3.7k input tokens (WORKER_SYSTEM is 10,152 chars, measured), completion capped at 3000, and no reasoning_effort or verbosity set anywhere in Agents_backend. A section under 80 words triggers a second serial call (workers.py:215-233).
-> merge_content (workers.py:359-494): pure Python, a few ms. It then makes 1 serial SEO structured-output call (~2.2k tokens in, 3-5 FAQ Q&As out), the only LLM call in the reducer.
-> images are off by default (generate_images=False); if on, decide_images (1 LLM call) and a serial image loop follow.
-> completion_validator + Fixes.py: regex and string work, ~ms, no I/O or sleeps. Not a latency source.
-> QA (1 call over up to 30k chars) plus up to 2x (revision + QA) -> keyword optimizer (0-1 full-article rewrite) -> G-Eval (1 call) -> optional media -> save. That is at least 4 serial LLM stages after approval (writers, SEO, QA, G-Eval).
Perceived latency: events carry only counts (workers.py:257-259), and the UI renders the article only from final_content, which is set at job completion (background.py:307-322, ContentView.tsx:262). The first visible article text therefore arrives after the whole pipeline.
Caveats: langgraph and langchain-openai are NOT installed locally, and the lock pins langgraph 1.2.9, langchain-core 1.4.9 and langchain-openai 1.3.5. Library behaviours below were checked only against upstream master via a web fetch, not the pinned tags. No pipeline timing exists in the repo, so every second figure is a labelled estimate.

### Quality control auditor and revision loop
*How latency is composed:* Gate flow (main.py 554-584): completion_validator -> qa_agent -> [if verdict==NEEDS_REVISION and >=1 critical issue and revision_count<2] revision -> qa_agent (full audit again) -> ... -> keyword_optimizer. Minor/suggestion issues never loop (main.py 568-577), so "skip re-audit on minor-only" already exists. Serial LLM calls per job: 1 QA call minimum; worst case QA,rev,QA,rev,QA = 5 (full-article fallback) or 3+2k (k = flagged sections, revised serially). Thesis fixtures: 0, 0 and 2 revisions (chapter5.tex 441-445), so the loop is the rare-but-expensive path and the single QA call is the every-run cost.
QA call (quality_control.py 144-194): one structured-output call on gpt-5-mini, ~10k input tokens (<=30,000-char article ~7.5k + 15 evidence x 500 chars ~2k + prompt), output = QAReport JSON. No reasoning_effort, verbosity or max-token cap is set anywhere (grep: only workers.py:197 max_tokens for writers). Wall-clock is therefore dominated by hidden reasoning + decode, not prefill; utils.py:132 itself calls the QA audit the slowest call observed. Trimming QA input (the 30k cap, evidence snippets) would save cost but little time, and the cap was raised on purpose for coverage (quality_control.py 41-45), so do not lower it.
Revision (revision.py 115-204): section path = one serial call per matched H2 section, each carrying ALL evidence; fallback = one call with the whole article in and the whole article out (~10k tokens each way for the 39,025-char fixture). Section matching depends on a field that is dropped upstream (see QC-2), so the fallback is probably the common path.
verify_citations (quality_control.py 48-110) is a single regex pass plus set lookups, no network: negligible (est. well under 10 ms), not a bottleneck. Event emits (append one JSONL line) and checkpoint writes are also negligible next to LLM time. No sleeps or polling in these two files; LLM timeout 180 s with 2 retries (utils.py 135-136), so a wedged call can cost up to ~9 min.
No benchmark data exists in the repo (usage.py records tokens only, no latency or reasoning tokens); all savings below are labelled estimates. langchain-openai is not installed locally (pinned 1.3.5), so parameter claims are marked unverified.

### Image planning and generation
*How latency is composed:* In-graph path (main.py:469-484, 543-544): worker fan-out -> reducer subgraph [merge_content -> decide_images -> generate_and_place_images] -> completion_validator -> QA (+revision loop) -> keyword_optimizer -> geval -> media. The image stage is fully serial and on the critical path. (1) merge_content already holds one gpt-5-mini SEO structured call (workers.py:469-473). (2) decide_images is one planner call on llm_fast (gpt-5-mini, no reasoning_effort/verbosity/max tokens: utils.py:157-159,173), whole merged_md in, N specs out (multimedia.py:31-44). (3) generate_and_place_images loops images one at a time (multimedia.py:216-277). Each image tries OpenAI dall-e-3 1024x1024 standard (default), gets a URL, then does a second HTTP GET (76,90-96). On any failure it tries Gemini (3 tries, sleeps 1-2/2-3/4-5 s), then Pollinations (25 s socket timeout). The OpenAI client has SDK-default timeout (600 s) and 2 retries (63-64). Placement is pure string work (ms). Nothing downstream consumes the image files: video uses Pexels and exporters embed at save time. Only the Markdown insertion has to precede evaluation. The manual Regenerate Images button (manual_tasks.py:211-216) runs the same two nodes standalone, so IMG-1 and IMG-5..10 help there too; IMG-2..4 only help the in-graph path. Defaults: UI sends 2 images, dall-e-3/standard/1024x1024 (App.tsx:25-30; slider max 5, ChatView.tsx:677); API default is 0 (schemas.py:15-16). Golden/thesis runs set generate_images=False (tests/golden/test_golden.py:115), so image-stage changes cannot move thesis scores. image_style is accepted but never forwarded to the API (multimedia.py:66-73), so the UI Style option has no effect. Estimates (unverified, measure): planner 8-30 s, dall-e-3 standard 8-20 s per image, so about 30-70 s of image stage for 2 images. To measure after one run, diff timestamps in data/events/<job>.jsonl (event_bus.py:55,214): planner = 'started' (multimedia.py:29) to 'Planned' (47); generation = 'Generating' (201) to 'completed' (279); SEO+merge = merger started to completed (workers.py:360,484). Newer GPT image models (e.g. gpt-image-1-mini, listed in the installed SDK docs) were not benchmarked here. ### Campaign generator (LinkedIn/X posts)
*How latency is composed:* Campaign node (Agents_backend/Graph/agents/campaign.py:66-107) is 3 gpt-5-mini calls in 2 serial rounds. Round 1 is the brief: the full article (default 7 sections x 350 words, about 3-5k tokens; capped at 100k chars) goes in and a ~350-token structured brief comes out (lines 40-63, 80). Round 2 is the LinkedIn post (150-200 words) and the X post (<280 chars) run in a 2-thread pool, each fed about 600 tokens of topic plus brief (88-99). None of the three calls sets reasoning_effort, verbosity or a token cap. The client (utils.py:157-159, 173) has timeout 180 s and max_retries 2. There is no disk, DB, sleep, polling or CPU work beyond about 4 JSONL event appends, so wall time is almost entirely LLM decode plus hidden reasoning tokens. Prefill of 3-10k tokens is a minor part, so article size is not the lever.
Graph position: keyword_optimizer -> geval_evaluator (1 judge call) -> campaign || video || podcast -> END (main.py:586-606). LangGraph runs these as one superstep, so campaign never extends wall-clock when video or podcast is also on. Its output is only persisted at set_job_completed (background.py:307-322).
The web UI hardcodes generate_campaign=false (ChatView.tsx:193). UI users therefore only reach campaign through POST /generate-social -> run_manual_task -> _handle_campaign (manual_tasks.py:188-208), where node latency is the whole wait. That path loads no evidence.json, so SUPPORTING EVIDENCE is empty.
Estimated node time, unmeasured: ~12-45 s, assuming default medium reasoning, 300-400 visible tokens per call and 80-150 tok/s decode.
